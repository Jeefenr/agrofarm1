# Дослідження: Імітаційний прототип агропідприємства

## Рішення: мінімальна версія JDK — 21

**Рішення**: Використовувати JDK 21 як мінімальне середовище розробки й запуску; README-команди компілюють код із `javac --release 21`.

**Обґрунтування**: Java 21 — LTS-версія, яка дає чітку відтворювану ціль для навчального застосунку та підтримується JDK без додаткового інструментарію. Предметній моделі не потрібні нові мовні можливості, тож реалізація лишається простою й сумісною з релізом 21.

**Альтернативи**: JDK 17 забезпечив би ширшу сумісність зі старішими середовищами, але специфікація не вказує на таке обмеження. JDK 25 — новіший LTS, але вимагав би новішого середовища без потреби з боку функцій прототипу.

**Довідка**: [Oracle Java SE Support Roadmap](https://www.oracle.com/java/technologies/java-se-support-roadmap.html), [довідка `javac` для Java 21](https://docs.oracle.com/en/java/javase/21/docs/specs/man/javac.html).

## Рішення: JDK-only консольний запуск без build-системи

**Рішення**: Розмістити виробничі джерела в `src/main/java/agrofarm`, а перевірки — в `src/test/java/agrofarm`. Використовувати один `DemoMain` як точку складання фіксованих даних і автоматичного сезонного сценарію. Компілювати класи однією командою `javac` із кодуванням UTF-8 та запускати через `java`.

**Обґрунтування**: Така структура дає чітке розділення коду й перевірок та відповідає вимогам компіляції з консолі, відсутності зовнішніх залежностей і автоматичного запуску без введення користувача. Наявний `.gitignore` уже виключає `out/` і файли `.class`.

**Альтернативи**: Maven або Gradle полегшили б масштабування, але додають конфігурацію та інструментарій, зайві для дев'яти предметних класів. Інтерактивний CLI суперечить зафіксованому рішенню щодо автоматичної демонстрації.

## Рішення: самодостатні перевірки без тестового фреймворку

**Рішення**: Додати тестовий клас із `main`, який перевіряє очікування явними умовами та кидає `AssertionError` у разі помилки; бізнес-кейси не покладаються на вимкнені за замовчуванням Java `assert`. Запуск демонстрації перевіряти окремо як наскрізний smoke test.

**Обґрунтування**: Специфікація задає конкретні граничні випадки, але забороняє зовнішні залежності. JDK-only перевіряльник дає змогу повторити перевірки поведінки зі стандартною командою `java`.

**Альтернативи**: JUnit надає розвинені засоби тестування, однак потребує сторонньої залежності або build-системи. Ручна перевірка лише виводу демонстрації не покрила б усі негативні умови й перевірку незмінності суми.

## Рішення: описати консоль як користувацький контракт

**Рішення**: Додати `contracts/console-demo.md` як контракт взаємодії з користувачем: точка запуску, відсутність аргументів/вводу, порядок сценарію, вимоги до повідомлень і відсутність побічних ефектів. Не створювати мережевий API чи контракт зовнішньої інтеграції.

**Обґрунтування**: Застосунок не інтегрується з іншими системами, але консоль є його явним користувацьким інтерфейсом, і його видима поведінка має бути перевірюваною.

**Альтернативи**: Не створювати контракт узагалі — це не документувало б поведінку CLI. Описувати штучний API або погодний сервіс — виходило б за межі специфікації.

## Вирішені невідомі

Специфікація не встановлювала версію Java, тестовий засіб і формат користувацького інтерфейсу. Для цього плану вибрано JDK 21, перевіряльник на стандартній Java та контракт автоматичної консолі. Команди README націлено на POSIX-сумісну оболонку; мережевий доступ, база даних і runtime-залежності не потрібні.
