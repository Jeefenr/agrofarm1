# План реалізації: Збереження даних агропідприємства через SQLite та Guice

**Гілка функції**: `004-sqlite-guice-storage` | **Дата**: 2026-11-13 | **Специфікація**: [spec.md](spec.md)

**Вхід**: специфікація функції у `specs/004-sqlite-guice-storage/spec.md`.

## Підсумок

Розширити наявний консольний прототип збереженням технічних операцій поля у файловій SQLite-базі та статичним HTML-звітом із фактичного стану бази. Залишити наявну послідовність демонстрацій і консольні повідомлення; додати стабільні ідентифікатори операцій, контракт збереження, SQLite-реалізацію, модуль Guice і генератор звіту. Maven керує збиранням та тестами з цільовою версією Java 21.

## Технічний контекст

**Мова/версія**: Java 21; Maven-компілятор налаштовано через `release=21`.

**Основні залежності**: Google Guice 7; Xerial `sqlite-jdbc`; JUnit Jupiter для автоматизованих тестів (test scope).

**Зберігання**: SQLite-файл `target/agrofarm.db`; статичний звіт `target/operations.html`. Обидва файли належать до результатів збирання й видаляються разом із `target`.

**Тестування**: `mvn test` із JUnit Jupiter та Maven Surefire; наскрізна перевірка демонстрації та HTML-звіту через Maven Exec Plugin.

**Цільова платформа**: Консольне середовище з JDK 21 і Maven 3.x; SQLite працює локально без окремого сервера.

**Тип проєкту**: Навчальний Java CLI-застосунок.

**Цілі продуктивності**: Спеціальні цілі не потрібні; обсяг даних обмежений демонстраційними сценаріями.

**Обмеження**: Зберегти чинні пакети, сценарії, порядок їх виконання й тексти українських повідомлень. Записувати окремі операції незалежно, ідентифікувати їх стабільним ключем, екранувати HTML-текст, явно повідомляти про помилки українською. Звіт не створюється при помилці читання; помилки окремих записів не скасовують інші успішні записи. Каталог `target` створюється перед використанням.

**Масштаб**: Один консольний застосунок, чинна модель поля й операції, інтерфейс сховища, SQLite-сервіс, Guice-модуль, генератор звіту та локальні автоматизовані тести.

## Підхід до дизайну

1. Додати до `TechOperation` стабільний ідентифікатор; під час сценарію передавати до `Field` сам об'єкт із призначеним сховищем. `Field` формує запис із ID операції, ID поля, типу та стану.
2. Описати доменний контракт методами збереження одного запису та читання всіх записів. Реалізація SQLite створює схему, виконує UPSERT за первинним ключем `operationId` та читає повний набір для звіту.
3. Налаштувати кореневий `DatabaseModule extends AbstractModule`: прив'язати контракт до SQLite-реалізації та надати JDBC-з'єднання. Для кожного демонстраційного поля створити дочірній Injector із параметрами ідентифікатора/назви та отримати `Field` через його `getInstance(Field.class)`; сервіс сховища успадковується з кореневого Injector. Закрити спільне з'єднання наприкінці запуску.
4. Зберігати кожну операцію окремим викликом, не об'єднуючи їх у спільну транзакцію. Помилка однієї операції повідомляється українською, а цикл продовжується. Після завершення спроб запису прочитати базу; при успішному читанні сформувати звіт із наявних рядків і попередженням про помилки запису.
5. Відокремити формування HTML від доступу до БД. Генератор створює `target/operations.html`, показує зрозумілий порожній стан і екранує всі атрибути, що вставляються як текст. Створення каталогу й запис файлу мають явно повідомляти про помилку українською.
6. Оновити README та обидві UML-діаграми. Перенести чинні перевірки до тестів, що автоматично виконує Maven, і додати тести повторного UPSERT, читання після повторного запуску, порожнього результату, HTML-екранування та часткової помилки запису.
