# Модель даних та відповідальностей

Цей документ описує концептуальні типи, які треба відобразити в `docs/class.mmd` і CRC-картках. Назви програмних типів та їхні ідентифікатори лишаються англійською; пояснення — українською.

## Типи

| Тип | Категорія | Дані й відповідальність |
|---|---|---|
| `FarmParticipant` | Абстрактний клас | Спільна ідентичність учасника та спільна поведінка/контракт дій щодо сезонного плану. Має конструктор для ініціалізації спільних даних. |
| `Agronomist` | Клас | Керує плануванням сівозміни та запитує сезонний аналіз через `CropYieldAnalysis`. Наслідує `FarmParticipant` і реалізує `IWorkPlan`. |
| `Operator` | Клас | Планує та фіксує польові роботи. Наслідує `FarmParticipant` і реалізує `IWorkPlan`. |
| `Storekeeper` | Клас | Обліковує надходження врожаю для поля та сезону. Наслідує `FarmParticipant` і реалізує `IWorkPlan`. |
| `Field` | Клас | Представляє земельну ділянку, пов'язаний сезонний план і дані поля. Володіє переліком `TechOperation`; зберігає надходження врожаю у контексті сезону без окремого класу для запису надходження. |
| `FieldWork` | Клас | Представляє заплановану чи виконану роботу з полем, сезоном і видом операції. Переводить роботу у виконану лише за наявності обов'язкових даних. Отримує `WeatherService` як явну залежність. |
| `CropYieldAnalysis` | Клас | Формує порівняння урожайності за полями для одного сезону на основі облікованих надходжень; відрізняє відсутність даних від нульової урожайності. |
| `WeatherService` | Клас | Надає внутрішній модельований погодний контекст для роботи; не звертається до зовнішнього сервісу. |
| `TechOperation` | Клас | Описує технічну операцію, що є складовою переліку операцій конкретного `Field`. Фізична дія лише планується/повідомляється. |
| `IWorkPlan` | Інтерфейс | Мінімальний контракт операції щодо сезонного плану, спільний для ролей. Не має CRC-картки. |

## Зв'язки та обмеження

- `Agronomist`, `Operator` і `Storekeeper` успадковують `FarmParticipant` та реалізують `IWorkPlan`.
- `Field` композиційно володіє своїми `TechOperation`; технічна операція не є самостійною частиною переліку іншого поля.
- `FieldWork` отримує `WeatherService` явно через конструктор; сервіс не створюється приховано як глобальний чи статичний об'єкт.
- `FieldWork` пов'язана з полем, сезоном та типом операції. Без обов'язкових даних робота не може мати стан «виконана».
- Надходження врожаю зберігається для поля та сезону без введення окремого типу запису надходження; повторні однакові дані не мають непомітно подвоювати облік.
- `CropYieldAnalysis` читає обліковані надходження лише для вибраного сезону. Якщо надходжень немає, результат позначає відсутність даних, не підміняючи її нульовою урожайністю.
- Якщо модельований прогноз погоди недоступний, це позначається окремо; прогнозні дані не подаються як фактичні умови.
- Усі класи мають конструктор і щонайменше один атрибут або метод. Інтерфейс має щонайменше одну операцію контракту.
- Діаграма класів показує принаймні один `final` метод, один перевизначений метод і один набір перевантажених методів.
- На кожен із дев'яти класів створюється CRC-картка з відповідальністю та співпрацею; для `IWorkPlan` картки немає.

## Стани роботи та сезонного циклу

`FieldWork` має відображати мінімум розрізнення запланованої та виконаної роботи. Перехід до виконаної роботи дозволено лише коли задані поле, сезон і тип операції. Сезонний цикл починається плануванням сівозміни, переходить до виконання робіт, потім до обліку надходжень врожаю; аналіз можливий після появи облікованих даних.

## CRC-співпраця

У колонці співпраці кожної картки вказуються лише типи, з якими клас безпосередньо взаємодіє. Відповідальності мають залишатися розділеними: планування через `Agronomist`, аналіз через `CropYieldAnalysis`, виконання робіт через `Operator`/`FieldWork`, облік надходжень через `Storekeeper`/`Field`, а модельований погодний контекст через `WeatherService`.
